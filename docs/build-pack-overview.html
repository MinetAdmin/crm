BD CRM Build Pack

Review of the scoping document “BD CRM: Requirements and Data Model, draft v0.1” and the twelve-document pack produced from it — everything needed to build the custom CRM from the ground up.

Pack v1.0 · 2026-09-09 · 12 documents + runnable PostgreSQL schema · repo: minet/crm/docs/

Verdict on the spec: unusually strong for a v0.1 — evidence-driven, with an essentially build-ready data model (the opportunity / revenue-schedule grain, stage–outcome split, derived-never-typed rollups, and day-one stage history are all correct and are adopted unchanged). What it lacks is everything an engineer needs on day one: architecture, non-functional requirements, API and UI definition, security model, test criteria, and a plan. This pack supplies those.

One dominant risk  Question I1 — must the CRM produce the CEO Summit pack, or only its New Business pipeline? — is a roughly 3× scope swing and is still open. The pack phases the work so Phase 1 is useful either way and the schema already carries Phase-2 landing zones.

What the spec settles, and what had to be added

Adopted unchanged

  • One pursuit = one Opportunity; money lives in dated revenue schedule lines beneath it
  • Stage separated from outcome, exit criteria per stage, stage-defaulted probability
  • Rollups, gaps and weighted amounts derived, never typed
  • Month-end forecast snapshots and the movement report
  • Stage history from day one — the one thing that can’t be added retrospectively
  • The §15 corrections: unit ⊃ sector, 50% committed threshold, monthly target phasing, typed support requests, Tender as its own entity

Added by this pack

  • Numbered, testable requirements (FR-*, BR-*, NFR-*)
  • Architecture & stack: TypeScript / Next.js / PostgreSQL on Azure, invite-only Entra SSO, one deployable, solo-dev posture
  • Runnable schema — validated end-to-end: constraints reject lost-without-reason, non-numeric amounts, mid-month dates
  • API contract, RBAC matrix & row visibility, field-level audit design
  • Screen inventory, report formulas defined exactly once
  • Migration gates with line-by-line money reconciliation; test plan; ~22-week solo-dev delivery plan

Six questions block migration — none block the build

The build track starts now. These need answers before data loads (target: weeks 1–4, at the controlled-list workshop and sponsor session):

  • I1Does the CRM produce the CEO pack, or only the New Business pipeline?Decides Phase 2 (~3× scope). Decision gate set at week 4; either answer is safe for Phase 1.
  • C1Are the amounts brokerage commission or gross written premium?Changes the meaning of every figure; schema isolates the change to one table.
  • C2What does “Effective Month” actually mean?Inception vs recognition vs payment = three different forecasts from identical data.
  • F1Which workbook is authoritative — BD RAW DATA.xlsx or _3.xlsx?They disagree (172 vs 157 initiative rows, a lost header, live #REF! errors).
  • F2Are the repeated client rows one deal or several?The opportunity grain — the one migration decision nobody outside BD can make.
  • A1Do individual owners carry revenue targets?Decides the target model and whether owner performance is answerable at all.

Three things the build must not cut

The spec’s own warning (§11): custom builds usually run out of budget exactly where the spreadsheets failed. All three are therefore launch acceptance criteria, not enhancements — descoping any of them requires the sponsor to strike them from the test plan in writing:

Non-negotiableHow the pack protects it
1Month-end forecast snapshots + movement reportImmutable copies, no UPDATE/DELETE grants; movement buckets must reconcile exactly; seeded-data proof at launch
2Field-level audit trailSingle write path through audit middleware, same transaction; overrides and reassignments surfaced in the UI
3Role-based visibilityServer-side scoping on every query from day one; the flippable choices are settings, not code
