# BD CRM

Custom CRM for the Minet Uganda Business Development team: leads, opportunity pipeline with a
revenue schedule, strategic initiatives, tenders, targets, forecasting with month-end
snapshots, and workload reporting.

**Start with [`docs/README.md`](docs/README.md)**: the full build pack (requirements,
architecture, data model, API, RBAC, reports, migration, tests, plan, decision log). The
source spec, `CRM review.pdf`, is kept in git history at commit 3ce7f35.

## Stack

Next.js (App Router) + TypeScript · PostgreSQL (SQL-first: `db/migrations/`, Prisma v6 client
generated by introspection) · Auth.js with invite-only Microsoft Entra ID SSO · Vitest ·
GitHub Actions. Hosting target: Azure Container Apps + Azure Database for PostgreSQL
(docs/03 §8, decision D-21 pending).

Note: Prisma is pinned to **v6** deliberately, because v7 replaced the classic
`db pull`/`generate` ORM workflow with a platform CLI. Revisit only as a deliberate decision.

## Local setup

```bash
# 1. Postgres (once)
brew install postgresql@18 && brew services start postgresql@18
createdb crmdev

# 2. Env
cp .env.example .env
# fill in AUTH_* values and put your username in DATABASE_URL
# (postgresql://$(whoami)@localhost:5432/crmdev)

# 3. Install, migrate, seed (reference lists + dev fixtures)
pnpm install
pnpm db:migrate
pnpm db:seed

# 4. Run
pnpm dev          # http://localhost:3000
pnpm verify       # lint + typecheck + tests
```

Entra setup for local sign-in: app registration (single tenant) with redirect URI
`http://localhost:3000/api/auth/callback/microsoft-entra-id`. Copy the secret **Value** from
Certificates & secrets, not the Secret ID; the Secret ID is a UUID and fails at token exchange
as `invalid_client`. No app assignment is needed. Access is decided by the `app_user` table:
on a database where nobody has signed in yet, your first sign-in creates you as `admin`
(see docs/03 §2.1), and everyone after that needs an invite from an admin.

## Layout

```
docs/            build documentation pack (source of truth for design decisions)
db/migrations/   forward-only SQL migrations (0001 = full schema from docs/schema.sql)
db/seed-*.sql    reference data (prod-safe) and dev fixtures
scripts/         migrate.ts, seed.ts
prisma/          schema.prisma generated via `pnpm db:pull`, never edited by hand
src/auth*.ts     invite-only Entra SSO (edge-safe split config)
src/lib/audit.ts field-level audit: every business write goes through withAudit
src/proxy.ts      session gate for all non-public routes (Next 16 proxy)
```

## Container and deployment

`pnpm build` needs no secrets: env validation is skipped during the build and
runs at startup instead, so a bad configuration stops the container with a
readable message rather than breaking the build.

```bash
docker build -t crm .
docker run --rm -p 3000:3000 --env-file .env crm
```

The image carries `db/` and `scripts/`, so migrations run from the same
artefact that serves the app:

```bash
docker run --rm --env-file .env crm pnpm db:migrate
```

CI builds the image on every run and publishes it to GitHub Container Registry
from `main` only. Hosting target is Azure Container Apps, with the scheduled
worker as a Container Apps Job and migrations as a job before each release
(docs/03 §8, decision D-21).

## Working rules (solo-dev discipline, docs/03 §2.2)

- Schema changes: new numbered file in `db/migrations/`, update `docs/schema.sql` to match,
  then `pnpm db:migrate && pnpm db:pull`.
- Every business-entity mutation goes through `withAudit`. There is no second write path.
- Stage changes only via the (upcoming) stage service endpoint, never a direct column update.
- A change isn't done until `pnpm verify` passes and any affected doc in `docs/` (especially
  `docs/12-decision-log.md`) is updated in the same commit.
